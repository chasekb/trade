# Live/paper-live parity fixture and acceptance-test contract

## Purpose

This note defines the fixture contract for proving that `live` and
`live_parity` use the same market-data, order-book, sizing, and preflight
inputs/decisions, while `live_parity` never submits a Coinbase order. It is a
test design, not runtime evidence and not a claim of live profitability.

The current implementation uses `SimulatedTradingService` for both synthetic
simulation and `execution_mode=live_parity`. `live_parity` is selected through
`POST /api/trading/simulated/start`; the controller accepts only `simulated` and
`live_parity` execution modes. `LiveTradingService` remains the real `mode=live`
path. There is no standalone SQL migration directory: both services currently
perform idempotent `ensureSchema()` DDL/backfill at startup.

## Existing seams and conventions

- Market input: `CoinbaseAdvancedClient::getTicker()` and
  `CoinbaseAdvancedClient::getOrderBook()` produce `MarketQuote`-equivalent
  values (`mid`, spread, best bid/ask, imbalance, volume, depth).
- Decision seam: `buildExecutionAnalysisLocked()` is the parity preflight
  boundary. It records `blocked`, `blocker_reason`, `executable_intent`,
  allocation, expected-return fields, and (for parity) minimum-notional,
  available-cash, and estimated-fee inputs.
- Paper fill seam: `openPositionLocked`, `addToPositionLocked`, and
  `closePositionLocked` settle locally. `live_parity` enters this path from
  `generateTickLocked()` and must not enter `dispatchOrders()`.
- Real order seam: `LiveTradingService::dispatchOrders()` and
  `SimulatedTradingService::dispatchOrders()` are the only order-dispatch
  boundaries to wrap with a spy. `CoinbaseAdvancedClient::placeMarketOrder()`
  is the submission call that must remain at zero for paper-live.
- Persistence: both services write `order_book_signals` and
  `individual_trades`; `LiveTradingService` additionally writes
  `live_coinbase_orders`. `is_closing_leg` is nullable by design so old rows
  remain distinguishable from explicit new classifications.
- Reconciliation: C++ `ExecutionReconciliation` and frontend
  `lib/executionReconciliation.ts` already define the counters and blocker
  buckets used by the fixtures.
- Frontend mode boundary: `buildStartTradingPayload()` carries
  `parameters.execution_mode`; `apiClient.startTrading()` must bypass local
  synthetic fallback for `live_parity` but may retain fallback for ordinary
  synthetic simulation. The simulated panel renders the mode warning and
  execution diagnostics.

## Canonical fixture bundle

Store fixtures under `test/fixtures/live_parity/` (or the repository's chosen
test-fixture directory) with one versioned manifest. The same manifest must be
fed to both live and paper-live harnesses; harness-specific output is separate.

```json
{
  "schema_version": 1,
  "session": {
    "session_id": "fixture-parity-001",
    "strategy": "orderbook",
    "symbols": ["BTC-USD", "ETH-USD"],
    "parameters": {
      "position_size_mode": "dollar",
      "position_size_value": 100.0,
      "round_trip_fee_percent": 0.16,
      "slippage_buffer_percent": 0.0,
      "minimum_net_pnl_usd": 0.0,
      "confidence_threshold": 0.0,
      "max_positions": 2,
      "account_position_management": "disabled"
    }
  },
  "quotes": [
    {
      "symbol": "BTC-USD",
      "sequence": 1,
      "valid": true,
      "mid": 65000.0,
      "best_bid": 64999.0,
      "best_ask": 65001.0,
      "spread": 2.0,
      "imbalance": 0.8,
      "volume": 10.0,
      "depth": 10
    }
  ],
  "signals": [
    {
      "symbol": "BTC-USD",
      "signal_type": "buy",
      "strength": 0.9,
      "expected_return": 0.02,
      "fee_adjusted_expected_return": 0.018,
      "win_probability": 0.7,
      "model_confidence": 0.9,
      "profitability_gate_passed": true
    }
  ],
  "account": {
    "cash": 1000.0,
    "cash_hold": 0.0,
    "holdings": [],
    "positions": []
  }
}
```

The quote fixture is authoritative input, not a response to be regenerated by
either mode. Add cases for: invalid/missing quote, sell signal, below-$1
notional, insufficient cash after pending reserve, existing position, maximum
positions, ML/profitability rejection, and exact-flat close with nonzero fee.
Use fixed timestamps and deterministic IDs in expected-output fixtures; never
assert wall-clock strings or random synthetic prices.

### Expected normalized decision record

Each harness should emit one normalized row per evaluated symbol/tick:

```json
{
  "mode": "live|live_parity",
  "session_id": "fixture-parity-001",
  "tick": 1,
  "symbol": "BTC-USD",
  "quote_input": {
    "mid": 65000.0, "best_bid": 64999.0, "best_ask": 65001.0,
    "spread": 2.0, "imbalance": 0.8, "volume": 10.0, "depth": 10
  },
  "signal": {"type": "buy", "strength": 0.9},
  "preflight": {
    "allocated_usd": 100.0,
    "estimated_fee": 0.16,
    "available_cash": 1000.0,
    "blocked": false,
    "blocker_reason": "paper_fill|<specific blocker>",
    "executable_intent": true
  }
}
```

Parity comparison ignores only mode labels, IDs, timestamps, and the final
execution label. It must compare all quote fields, signal fields, sizing inputs,
preflight fields, blocker reason, and executable-intent result byte-for-byte
(or numerically within an explicit `1e-9` tolerance for doubles).

## Test matrix

### 1. Shared market and preflight inputs

- Feed the identical quote sequence and session parameters into the live and
  live-parity decision harnesses.
- Assert identical normalized quote/order-book records for every symbol and
  tick, including bid/ask, spread, imbalance, volume, and depth.
- Assert identical signal type/strength and all ML/profitability inputs.
- Assert identical allocation, fee, available-cash, minimum-notional, and
  blocker decisions for every positive and blocked case.
- A missing or invalid quote must produce no live-data tick and no intent in
  either harness; it must never fall back to synthetic data.

The implementation should introduce a dependency-injection seam around public
quote acquisition and an injectable order executor. Do not mock the strategy
or preflight functions: parity is only meaningful if both modes run the same
production decision code.

### 2. Paper execution has zero Coinbase submissions

- Start `live_parity` with a spy `CoinbaseAdvancedClient` whose public quote
  methods replay the fixture and whose `placeMarketOrder()` fails the test if
  called.
- Run buy/open, add, close, blocked, and stop/settle scenarios.
- Assert the submission spy count is exactly zero and the public quote spy
  count matches the expected quote requests.
- Assert paper fills are present in the simulated in-memory result and
  `individual_trades` rows have `trade_type=live_parity` (or the documented
  paper-live value), with no `live_coinbase_orders` row.
- Run the matching real-live harness with an order executor spy; assert only
  the explicitly enabled `mode=live` plus `live_order_execution=true` path can
  submit, and that disabled credentials/flag remain fail-closed.

The zero-call assertion must be on the order-submission method, not merely on
HTTP request counts: public quote requests are expected in parity mode.

### 3. Blocked intents and summary counters

For a mixed fixture containing holds, generated blockers, executable intents,
opens, closes, and an exact-flat close, assert:

- `signals_evaluated` counts every valid evaluated signal row.
- `signals_generated` excludes holds.
- `executable_order_intent_count` counts only accepted preflight intents.
- `execution_blocker_counts` preserves every reason and count, including
  `below_minimum_notional`, `insufficient_cash`, `spot_cannot_open_short`,
  `existing_position`, `pending_order`, `max_positions`, and ML/profitability
  gates.
- `closing_legs` includes an exact-flat gross close; after fees it is a loser.
- Winners, losers, win rate (0-100), average win/loss, expectancy, profit
  factor, total PnL, and total fees match `ExecutionReconciliation` semantics.
- Outcomes without an executable intent are marked unexplained rather than
  silently treated as successful reconciliation.

### 4. Fills and accounting isolation

- Open and close the same symbol in synthetic, live-parity, and real-live
  fixture harnesses. Assert live-parity cash, positions, fees, realized PnL,
  and trade rows are isolated from synthetic and real-live sessions by
  `session_id` and `trade_type`.
- Assert paper opens use local fill price/fee rules and do not call Coinbase
  authenticated order endpoints.
- Assert real-live fill tests use the Coinbase fill's filled quantity,
  average price, and charged fee; never substitute paper fees.
- Assert pending cash reservations are subtracted once and released once on
  terminal paper/live outcomes.
- Assert account-level inherited holdings are not treated as synthetic session
  capital, and exits-only management cannot create new strategy entries after
  the inherited quantity is gone.

### 5. Mode and API validation

Backend contract tests must cover:

- `execution_mode=simulated` starts synthetic mode.
- `execution_mode=live_parity` starts Coinbase-public-data paper mode.
- Unknown execution modes return a client error and do not start a worker.
- `mode=live` routes to `LiveTradingService`; it never silently routes to
  simulated or local fallback.
- Legacy simulated route aliases (`/api/simulated-trading/start` and
  `/api/simulated-trading/stop`) remain equivalent to canonical routes.
- Status/portfolio payloads include mode, execution-is-paper, market-data
  source, session ID, positions, counters, and blocker counts.
- Old clients omitting `execution_mode` retain synthetic simulation behavior;
  old clients sending supported legacy fields still receive the documented
  response envelope.

### 6. Persistence migration and legacy records

Because schema setup currently happens in `ensureSchema()`, migration tests must
run against three database states: empty schema, current schema, and a legacy
schema populated before `is_closing_leg` existed.

- Empty schema creates `order_book_signals`, `individual_trades`, and (live
  only) `live_coinbase_orders` with the documented nullable classification.
- Legacy `individual_trades` rows survive unchanged, including `NULL`
  `is_closing_leg`; startup is idempotent on a second run.
- The backfill must be explicit and covered: only rows proven to have an
  unambiguous closing classification may be backfilled. Rows whose old
  `pnl != 0` was previously used as a proxy must remain nullable rather than
  being guessed as closing legs.
- `trade_type` values `simulated`, `live_parity`, `live_paper`, and `live` are
  preserved and filtered independently by stats/reconciliation queries.
- Malformed legacy signal JSON cannot abort an entire stats/reconciliation
  query; tests must include malformed text and verify safe exclusion plus a
  diagnostic count.
- Migration/backfill failures fail closed for the affected write/query and
  emit an actionable error; they must not fabricate balances or fills.

If runtime DDL is retained, the eventual implementation should split schema
migration from service startup or provide a transaction/version table. Tests
must still prove repeated startup is safe and that two services cannot apply a
partially conflicting migration.

### 7. Frontend state and rendering

Using mocked `fetch` responses and the existing Jest conventions:

- `buildStartTradingPayload` preserves `execution_mode=live_parity` and does
  not send synthetic capital fields to real live mode.
- `apiClient.startTrading('simulated', ..., {execution_mode:'live_parity'})`
  calls the backend path and never activates the local synthetic fallback.
- Ordinary synthetic simulation may use the local fallback only when the
  backend is unavailable; a failed live-parity backend start must remain an
  error, not silently become synthetic.
- Simulated panel renders the explicit Coinbase live-data paper warning,
  active mode, market-data source, evaluated/generated/executable counters,
  and blocker buckets using `??` so zero is displayed.
- Status transitions (starting, active, stopped, rejected) do not leave a
  stale live-parity session flag or expose live order controls.
- Reconciliation tables render mode/trade-type scoped counters, exact-flat
  losses, unexplained outcomes, and empty/zero values without `NaN` or hidden
  rows.
- Existing live-tab normalization continues to use Coinbase portfolio fields
  as the source of truth; simulated fields never populate live balances.

## Mocking boundaries and anti-false-positive rules

1. Mock transport and time, not business decisions. Replay quote/order-book
   responses at the `CoinbaseAdvancedClient` boundary and inject a clock.
2. Use a recording order executor with a hard failure on any paper submission.
   A test that only mocks HTTP globally can miss an accidental direct client
   call.
3. Use an isolated database/schema or transaction per test. Assert rows by
   `session_id` and `trade_type`, not only total row counts.
4. Compare normalized decision records before comparing fills. Fill IDs and
   timestamps are intentionally mode-specific.
5. Keep synthetic fixtures separate from public-quote fixtures. Any synthetic
   fallback during a parity test is a test failure, not a permissible
   approximation.
6. Test both sides of every gate with the same input except for the one field
   under test; this prevents a passing test from proving only the happy path.
7. Add a negative assertion that no authenticated Coinbase endpoint is called
   by paper-live, while allowing the expected unauthenticated public quote
   calls.

## Measurable acceptance criteria

A future implementation is ready for review only when all are true:

- [ ] One versioned fixture manifest drives both live and live-parity harnesses.
- [ ] At least one happy-path open/close, one add, and one invalid-quote case
      compare all normalized quote and preflight fields.
- [ ] At least seven blocker cases are covered, including minimum notional,
      cash, spot short, existing position, pending order, max positions, and
      ML/profitability gates.
- [ ] The parity order-submission spy records exactly zero calls across all
      paper-live cases, including close and stop/settle.
- [ ] The real-live spy proves submission remains gated by `mode=live` and
      explicit `live_order_execution=true`.
- [ ] Mixed fixtures assert every summary counter and blocker bucket, plus
      exact-flat fee-negative close and unexplained-outcome behavior.
- [ ] Empty/current/legacy database migration tests pass, are idempotent, and
      preserve nullable legacy classification and trade-mode isolation.
- [ ] Legacy API aliases and old payloads are tested, while unknown modes are
      rejected without starting a worker.
- [ ] Frontend tests prove live-parity cannot fall back to synthetic data,
      render zero-valued counters, and keep live balances sourced from Coinbase.
- [ ] `git diff --check`, the focused C++ test targets in CI, and the focused
      frontend Jest/type checks pass. No local CMake/Docker build is required
      under the repository's remote-only delivery policy; exact-SHA remote CI
      is the final implementation gate.
- [ ] Runtime parity and live-account safety evidence remain separate from unit
      test evidence; passing fixtures alone does not authorize live trading.

## Suggested implementation order

1. Add deterministic fixture types/manifest and quote/order-executor seams.
2. Add C++ parity, zero-submission, blocker, fill, accounting, and migration
   tests; register focused targets in `CMakeLists.txt`.
3. Add API contract tests for modes, aliases, old payloads, and status fields.
4. Add frontend fetch/state/rendering tests, especially no live-parity fallback.
5. Run the focused suite in remote CI, inspect exact-SHA results, then collect
   a separately identified runtime parity window before closing the broader
   trading backlog item.
