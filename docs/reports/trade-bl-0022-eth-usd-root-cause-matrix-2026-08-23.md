# TRADE-BL-0022: ETH-USD root-cause matrix and safe correction options

Date: 2026-08-23 UTC
Scope: read-only investigation; no live orders, account mutations, code fixes, or local builds/tests.

## Executive finding

The observed Live Trading ETH-USD row is not a frontend phantom. Read-only captures at 2026-08-23T04:12:06Z, 05:12:23Z, 05:15:05Z, and 05:15:20Z agree across `/api/live-portfolio/status`, `/api/trading/live/positions`, `/api/trading/live/status`, and the frontend proxy: Coinbase reported `available=8.4078200000000004e-09`, `hold=0`, and approximately `$0.0000199` of ETH-USD value. The session was stopped/inactive, with no pending order, no managed quantity, and no managed floor. Persisted inspection found no filled `live_*` ETH order; the row is an inherited Coinbase dust holding.

A genuine Coinbase-absent row can nevertheless be retained by local state. The principal paths are: a failed account snapshot (the prior `positions_` read model is served), an accepted pending order awaiting settlement, an active managed-quantity floor (up to 30 successful snapshot cycles), or a stopped session that has not yet performed a final refresh. A successful snapshot that omits ETH-USD removes it when neither pending protection nor a floor applies.

## Explicit downstream answers

- **Portfolio totals:** Yes, a confirmed holding contributes to Coinbase `positions_value` and `total_value`. A stale/floor-protected local row also contributes to local `buildPortfolioJson()` totals. The nested live-tab `portfolio` is snapshot-based and can disagree with the local `positions` array during stale/floor conditions.
- **Cash:** No direct cash mutation occurs merely because a row is displayed. `cash_` and `cash_hold_` come from the Coinbase snapshot (`LiveTradingService.cpp:1306-1308`). Pending orders can reserve cash separately, but the observed ETH row had `pending_reserved_cash=0`.
- **Position value / equity:** Yes. `CoinbasePortfolio.cpp:35-40` and local directional value use quantity × current price. The observed dust impact is approximately `$0.00002`.
- **Unrealized PnL:** The observed inherited/unmanaged row contributes zero. Snapshot application and mark-to-market set PnL to zero for unmanaged holdings (`LiveTradingService.cpp:1381-1390`, `:1959-1968`). A retained managed floor can affect local PnL inputs and must be tested separately.
- **Risk / managed position limits:** It does not consume the managed strategy-position limit: `managedPositionCountLocked():482-485` counts only `session_managed` positions. It can still block a fresh open for the same symbol (`openPositionLocked():1997-2000`), and add/close behavior is gated by inherited-management settings (`:2063-2066`, `:2114-2119`). There is no separate margin engine in this spot path.
- **Exposure:** Yes for local in-memory status. `buildPortfolioJson():2446-2507` iterates every retained position and adds directional value and absolute exposure (`:2476-2479`, `:2495-2496`). A true phantom therefore remains risk/exposure-bearing until successful cleanup or expiry.
- **Pending reserves:** Not for the observed row. Pending symbols/reserved cash are maintained by queue/fill/recovery paths (`:638-645`, `:654-659`, `:1023-1026`); the capture showed none.
- **Persistence:** The position itself is primarily an in-memory serving read model. Persisted pending orders/trades can cause recovery behavior, but inspection found no filled live ETH trade and 33 ETH `live_coinbase_orders`, all rejected; 6,009 ETH trade rows were simulated/historical.

## Root cause classification

1. **Observed state:** Coinbase-confirmed inherited dust; not frontend-only, stale-internal, pending-settlement, or session-managed.
2. **Underlying defect class:** local serving state is retained across failed reconciliation and intentional settlement grace without a sufficiently prominent/strict distinction between Coinbase-confirmed and locally retained/stale state. `positions_` is serialized by direct positions/status endpoints even when the latest account snapshot is unavailable or a floor is active.
3. **Not supported by evidence:** a live filled ETH order, a persisted live-session trade causing the row, cash corruption, or a frontend-only duplication.

## Smallest safe correction options, ranked

1. **Lowest risk / first:** add provenance and stale-age presentation plus fail-closed action gates. On fetch failure, never label the old row `coinbase_confirmed`; expose snapshot error/staleness and suppress manual strategy actions that require current account authority. Do not clear positions on fetch failure, because clearing could hide real holdings and break reconciliation.
2. **Low-to-medium risk:** add offline seams and make successful-snapshot cleanup/floor behavior explicit. Keep pending protection only while an explicit persisted pending order exists; mark floor-protected rows `awaiting_snapshot_reconciliation` and exclude them from strategy eligibility/risk exposure until confirmed, while retaining authoritative accounting separately. This changes risk semantics and needs high-risk review.
3. **Medium risk:** shorten or remove the 30-snapshot managed floor only after measuring exchange settlement behavior. Removing it without a replacement can erase a real just-filled holding and misstate exits; retaining it without labeling creates the current phantom risk.
4. **Display-only product option:** hide sub-cent dust from the open-position presentation with an explicit display threshold, while preserving Coinbase accounting and liquidation/minimum-notional guards. Never silently remove it from equity or local authoritative state.
5. **Do not do:** delete the currently observed ETH-USD row or mutate Coinbase state. Read-only evidence confirms the balance exists at Coinbase and cleanup would be an approved live-account action, not a bug fix.

## Required regression coverage before any code correction

- Snapshot fixture: present ETH-USD creates inherited quantity; absent ETH-USD removes an unprotected row.
- Fetch-failure fixture: prior row remains internally available, error/stale provenance is serialized, `coinbase_confirmed` is not asserted, and no unsafe manual action is enabled.
- Managed-floor fixture: absent holding is retained for exactly 30 successful snapshots, expires on the expected cycle, and is excluded/included in exposure according to the chosen correction contract.
- Pending lifecycle fixtures: accepted order through stop/restart; partial/full fill; zero-fill terminal; complete-not-found after 30 misses; persistence failure and retry; pending symbol and reserved cash clear exactly once.
- Fill/snapshot ordering: `account_snapshot_reflects_fill=false` local application followed by refresh does not double-count or resurrect quantity.
- Portfolio invariants: cash unchanged by display-only stale rows; Coinbase portfolio totals versus local positions are explicitly distinguished; position value and absolute exposure use signed/absolute quantity correctly; unmanaged PnL remains zero; managed count and same-symbol entry gates remain correct.
- Lifecycle/status: stop without refresh retains accepted settlement state, restart waits for worker completion, successful restart clears stale rows, and status refresh neither masks a snapshot error nor reintroduces an erased row.
- Account-management eligibility: inherited holding and `manage_account_exits` transitions preserve `session_managed` and `eligible_for_strategy_management` semantics.
