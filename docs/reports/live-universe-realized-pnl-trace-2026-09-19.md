## Executive path

1. `PredictController` routes live session start/status/order endpoints to `trading::LiveTradingService` (`include/api/PredictController.hpp:38-46,100-111`; `src/api/PredictController.cpp:1372-1387`). `startSession()` reads the user payload, preserves the submitted `symbols` array (defaults only when empty), accepts `parameters` or legacy `strategy_params`, rejects synthetic-capital keys, requires `live_order_execution=true`, fetches a Coinbase account snapshot, establishes the starting capital baseline, recovers persisted pending orders, then starts `workerLoop()` (`src/trading/LiveTradingService.cpp:3010-3170`).
2. Each worker iteration first resolves accepted/recoverable pending orders, flushes queued writes, checks stop/shutdown state, requests the full selected universe via `selectLiveQuoteBatchLocked()` (no symbol cap), fetches Coinbase order books serially, refreshes the account snapshot, generates signals under the mutex, takes pending writes/intents, then dispatches exchange orders and flushes Postgres writes outside the mutex (`src/trading/LiveTradingService.cpp:2541-2668`). The cadence is therefore quote-fetch duration plus processing; there is no normal cadence sleep. Stop settling uses one-second sleeps only after stop was requested while accepted orders/writes remain.
3. `fetchLiveQuotes()` requires a configured exchange client and a successful Coinbase order-book response. A failed symbol is logged and omitted; an omitted/invalid quote produces no signal or order (`src/trading/LiveTradingService.cpp:1263-1295,2466-2477`). Each successful quote supplies mid, spread, bid/ask, imbalance, bid+ask volume, and depth.
4. `buildSignalRecordLocked()` maintains per-symbol price history (maximum 512), derives order-book or indicator-family signals, and emits the signal payload with signal type, strength, reason, `data_status`, prediction, spread/volume/imbalance, criteria analysis, ML analysis, and strategy metadata (`src/trading/LiveTradingService.cpp:1571-1682,1700-1985`). Order-book strategies use imbalance; `orderbook` and `ml_enhanced_orderbook` use the 0.22 activity floor, while `ml_orderbook_opportunity` considers every tick and relies on the profitability gate. Default order-book economics are 1.5% round-trip fee fraction and 0.2% slippage buffer; configurable keys are `round_trip_fee_percent` and `slippage_buffer_percent` (`src/trading/LiveTradingService.cpp:44-59,1873-1881,1923-1930`).
5. The shared diagnostics normalization adds spread, fee, and slippage to `required_edge`. A generated signal that is not actionable is rewritten to `hold`, `signal_generated=false`, strength zero, `prediction=HOLD`, and `data_status=sufficient`; this is an important divergence between raw/generated candidate activity and executable intent (`src/trading/LiveTradingService.cpp:1903-1952`; `src/trading/DiagnosticsContract.cpp`; `include/trading/DiagnosticsContract.hpp:45-93`).
6. `buildEntryExecutionAnalysisLocked()` records both the candidate and every blocker. It re-evaluates the diagnostics gate, ML confidence/expected-return gate, account readiness/management mode, existing position, pending order, max positions, finite positive size/price, Coinbase minimum quote notional, spot-side restriction, available holdings, available cash minus pending reserves, estimated fee, and explicit live-execution confirmation (`src/trading/LiveTradingService.cpp:2039-2151`; `src/trading/ExecutionPreflight.cpp:9-63`). Only `executable_intent=true` reaches `openPositionLocked()` or the close/reopen path.
7. `openPositionLocked()` applies account-managed entry policy, existing/pending position checks, `max_positions_` (default 100), position sizing, minimum notional, spot buy-only opening, cash plus 0.05% estimated fee, and explicit execution enablement before queueing an `OrderIntent` (`src/trading/LiveTradingService.cpp:2223-2281`; `src/trading/PositionSizingPolicy.cpp:100-126`). `closePositionLocked()` only closes session-managed positions, requires no pending order, available managed quantity, and execution enablement (`src/trading/LiveTradingService.cpp:2336-2383`). Stop-loss/take-profit use `stop_loss_percent`/`stop_loss` and `take_profit_percent`/`take_profit`; zero disables each (`src/trading/LiveTradingService.cpp:2164-2211`). Existing Coinbase holdings are never auto-liquidated by an ordinary session; explicit liquidation is separate and enforces pending, active/execution, available quantity, finite positive reference price, and minimum notional (`src/trading/LiveTradingService.cpp:2386-2455`).
8. Queueing inserts a per-symbol pending marker and reserves cash. Dispatch first persists a `live_coinbase_orders` row with serialized signal/position state, then calls Coinbase `placeMarketOrder`; definitive rejection releases the reservation, while uncertain failures remain pending for client-ID lookup. Accepted orders remain pending until fill lookup succeeds (`src/trading/LiveTradingService.cpp:689-703,910-1087,1089-1157`; `src/exchange/CoinbaseAdvancedClient.cpp:399-437`).
9. `resolvePendingLiveOrders()` recovers missing order IDs by client ID (30 complete-not-found attempts before releasing), obtains actual fill details including filled size/value/average price/total fees, applies the fill once, flushes the trade write, then marks the persisted order terminal. It refreshes the Coinbase account snapshot after any settlement (`src/trading/LiveTradingService.cpp:1160-1260`). The exchange parser fails closed on malformed/non-finite/negative fill numbers and requires value, average price, and actual fees for a positive fill (`src/exchange/CoinbaseOrder.cpp:60-101`; `include/exchange/CoinbaseOrder.hpp:20-30`).
10. `applyLiveFillLocked()` clears pending reservation, creates one `TradeRecord`, and updates position/accounting. Entry/add fills carry zero realized PnL and actual fees; close fills compute gross PnL from managed entry basis and add actual fees to `total_fees_`; inherited holding closes are tagged `live_account_managed_close` and PnL-excluded. Liquidations are tagged `live_liquidation`, zero PnL, and PnL-excluded. The closing-leg flag is true for ordinary closes and liquidations (`src/trading/LiveTradingService.cpp:705-908`).
11. Trade writes persist `trade_id, session_id, symbol, side, size, price, timestamp, strategy_type, signal_reason, pnl, fees, win_probability, expected_return, model_confidence, trade_type, is_closing_leg` to `individual_trades`; signal writes persist order-book fields and serialized payload to `order_book_signals`. Failed DB writes are re-queued (`src/trading/LiveTradingService.cpp:1450-1568`).
12. Runtime status exposes `cash_balance`, `cash_hold`, `available_balance_usd=cash-pending_reserved_cash`, positions, recent signals/trades, `realized_pnl`, `unrealized_pnl`, `total_fees`, and execution blocker counts. `stats` reloads the session's persisted `individual_trades`, excludes `live_account_managed_add/close` and `live_liquidation`, and falls back to in-memory inputs only if persistence is empty/unavailable (`src/trading/LiveTradingService.cpp:2678-2898`). `TradingStatsCalculator` treats persisted `pnl` and `fees` separately; net PnL is total PnL minus total fees, win rate is percent, and zero-PnL opening legs are excluded from win/loss denominators (`src/trading/TradingStatsCalculator.cpp:80-150`).

## Blocker/suppression matrix

- No credentials/configured exchange client: session start or account refresh fails closed; live-tab readiness reports credentials/account blockers.
- Account snapshot unavailable/stale: no session start; per-signal `account_not_ready` blocks intent. Quote failure is logged and suppresses that symbol for the tick.
- Selected universe/coverage: all submitted symbols are requested every worker tick; no enforced symbol cap. `requested_symbol_count`, attempted/succeeded/skipped counts, current batch, `coverage_complete`, and `quote_fanout_warning_threshold=10` are emitted. The warning is diagnostic only, not a cap (`src/trading/LiveTradingService.cpp:2799-2824`).
- Insufficient data/warm-up: indicator reasons containing `insufficient price history` or `warming up` set `data_status=insufficient`; no live signal is produced until a valid quote exists. Transformer inference reports `warming_up` and neutral outputs until its lookback is ready (`src/trading/LiveTradingService.cpp:148-151,1750-1775,1833-1839`).
- Activity/profitability: below activity or required edge becomes `hold`/`negative_fee_adjusted_edge`/`below_required_edge`; valid market data remains `sufficient`, so this is a strategy no-trade, not a coverage failure.
- ML gate: `ml_enhanced_orderbook` defaults to confidence threshold 0.6; transformer-only packs use `transformer_min_expected_return_percent` default 0.05. Heuristic fallback honors `fallback_to_baseline` default true (`src/trading/LiveTradingService.cpp:1988-2036`).
- Account position management: existing account holdings may be exits-only/unmanaged; entries can be blocked by `account_position_management_disabled`, and ordinary strategy closes refuse non-session-managed holdings.
- Existing position/pending order/max positions: `existing_position`, `pending_order`, and `max_positions` suppress duplicate/concurrent entries. Reservations are deducted from available cash exactly once.
- Min-notional/size/price: non-finite/nonpositive values and quote notional below `coinbaseMinQuoteOrderUsd()` fail closed. Explicit holding liquidation also checks estimated notional before enqueueing.
- Holdings/side/cash: spot cannot open shorts; sell requires available holdings; buy requires cash >= allocated USD + estimated 0.05% fee. Actual fees are taken from the exchange fill, never synthesized after acceptance.
- Explicit live execution: both session start and per-intent preflight require `live_order_execution=true`; manual endpoints also require active session and enabled execution.
- Persistence/order recovery: inability to persist an intent prevents exchange submission; malformed recovered order state aborts recovery/session start; uncertain exchange outcomes remain pending rather than being treated as rejected or filled.

## Field lineage and divergences

- Candidate signal: in-memory `SignalRecord` and `order_book_signals.signal_data` contain signal identity, side/type, strength, market fields, criteria, ML prediction, fee-adjusted expected return, diagnostics, and `trade_type=live`.
- Executable intent: `execution_analysis` is attached to the signal and adds `blocked`, `blocker_reason`, `allocated_usd`, `available_cash`, `estimated_fee`, `minimum_notional`, `required_edge`, and `executable_intent`. A generated signal can be persisted while being rewritten to HOLD by profitability normalization or blocked later by account/risk/execution preflight.
- Exchange order: `live_coinbase_orders` adds client/order IDs, amount units (quote for buys, base for sells), action, reservation, serialized signal/position snapshot, and lifecycle status. It is the authoritative recovery/audit bridge, not a fill.
- Fill/trade: `individual_trades` contains actual size/price/fee and `is_closing_leg`. Opening/add/liquidation rows are not realized outcomes; ordinary managed closes carry gross PnL in `pnl` and actual fees in `fees`; stats derive net PnL as gross PnL minus fees.
- UI status: the live producer exposes Coinbase snapshot fields and separate strategy-session status. `available_balance_usd` subtracts pending reserves, while raw `cash_balance` does not. Order-book API rows may include response-only missing symbols with HOLD/epoch timestamps; those placeholders are never persisted and never create intents (`src/trading/LiveTradingService.cpp:3485-3605`).

## Confirmed, ruled out, and unknown

Confirmed from source: selected symbols are not silently capped; quote cadence has no normal sleep; live orders require explicit confirmation and account readiness; failed quotes do not trade synthetic data; pending orders reserve cash and suppress same-symbol duplicates; actual Coinbase fills/fees are required; inherited/liquidation rows are excluded from realized-PnL stats; persisted session rows are preferred for stats; diagnostics distinguish signal generation from executable intent.

Ruled out by this trace: a missing UI row alone cannot prove missing execution (placeholders are response-only); `total_signals` is not cumulative signal history; a generated non-HOLD signal is not evidence of an order submission; an accepted Coinbase order is not evidence of a fill or realized PnL; a zero PnL opening leg is not a realized loss.

Still requires runtime data: selected-universe payload and effective parameter values for the incident session; quote fetch success/failure and latency logs; `order_book_signals.execution_analysis`; `live_coinbase_orders` lifecycle rows; Coinbase order/fill IDs and actual fees; `individual_trades` rows including `trade_type`/`is_closing_leg`; account snapshots around fills; and the exact frontend request/normalization path. Without those correlated session IDs/timestamps, a single blocker or suppressed-symbol count cannot be attributed to a specific incident.
